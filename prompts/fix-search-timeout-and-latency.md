# Fix Lopsis search timeout and latency

## Goal

Make the Sanity Context MCP-backed Lopsis search route complete reliably instead of aborting at 25 seconds, while reducing unnecessary model/tool latency and preserving grounded, structured lesson and video-moment results.

## Skills and guidance read

- `AGENTS.md` at the repository root.
- `sanity-best-practices` and its Next.js and GROQ references, for server-only Sanity access and efficient projected queries.
- `create-agent-with-sanity-context` and its Next.js agent reference, for initial-context caching, MCP tool selection, and Vercel AI SDK integration.
- `dial-your-context`, to review whether the Context document itself is causing redundant tool behavior. Its pure-delta rule confirms the current document should stay concise; this task will not rewrite the document unless live evidence shows a specific instruction is required.
- Installed Next.js 16.3.3 documentation for Route Handlers and `maxDuration`. Deployment platforms may terminate long-running handlers, and `maxDuration` is the route-level declaration platforms can honor.

## Existing code and configuration inspected

- `app/api/search/route.ts`: starts one 25-second abort timer before MCP setup, initial-context retrieval, Gemini tool use, structured output generation, and Sanity grounding. It exposes all MCP tools except `initial_context`, allows up to eight model steps, and has no exported platform `maxDuration`.
- `lib/search/context.ts`: validates the Sanity Context URL, creates a fresh MCP client per request, fetches `/initial-context`, and caches the initial context for five minutes.
- `lib/search/prompt.ts`: correctly requires MCP use, tokenized wildcard matching, reverse course lookup, chapter-first video matching, transcript fallback, narrow projections, and grounded IDs/timestamps.
- `lib/search/ground-results.ts`: re-fetches candidate IDs and exact timestamps from Sanity before returning cards, preventing invented model output from reaching the UI.
- `lib/search/schema.ts`: validates request, candidate, and response contracts with Zod.
- `components/search-page.tsx`: calls the route from the browser and already displays the route's safe timeout error.
- `studio/scripts/seed/search-context.ndjson`: the Context instructions already contain the essential relationship and query deltas; they do not contain general conversational guidance that obviously explains the timeout.
- `package.json`: Next.js 16.3.3, AI SDK 6, `@ai-sdk/mcp`, and the Google provider are already installed.
- The working tree contains substantial unrelated and in-progress changes. Preserve them exactly.

## Diagnosis

- The observed 504 is generated by Lopsis itself: the route aborts the complete multi-stage operation at exactly 25 seconds.
- A tool-using structured-output request can require several Gemini round trips. Allowing eight steps and exposing `schema_explorer` even though the schema is already injected leaves room for avoidable tool calls.
- Raising only the timer would reduce 504s but would leave the agent unconstrained and provide no evidence about where time is spent.
- Replacing the MCP/LLM path with a direct hard-coded Sanity query would violate the approved Lopsis search architecture and is out of scope.

## Decisions and assumptions

- Keep Google Gemini, Sanity Context MCP, generated GROQ, Zod structured output, and server-side grounding.
- Give the route a 60-second platform budget and use an internal deadline slightly below it so Lopsis can still return its sanitized 504 response before the host terminates execution.
- Expose only `groq_query` to Gemini. The cached initial context already supplies the schema, so `initial_context` and `schema_explorer` are unnecessary in the normal search path.
- Reduce the model step ceiling to the smallest value proven by live tests to support: one primary lesson/chapter query, an optional transcript-fallback query, and final structured output. Start with four steps and increase only if an evidenced valid search requires it.
- Strengthen the inline prompt with an explicit tool-call plan rather than changing the product behavior: combine lesson and chapter discovery where practical, query transcript chunks only when chapter matching fails, and do not inspect the schema again.
- Add safe stage timings for MCP/context setup, Gemini/tool execution, and grounding. Do not log learner query text, credentials, tool arguments, raw model output, or content payloads.
- Preserve the five-minute initial-context cache unless timing evidence identifies it as a problem. Do not cache user search responses or share per-request MCP clients across invocations.
- Propagate browser/request cancellation into outbound work so abandoned searches stop consuming model and MCP resources.
- Keep the existing safe 400, 502, 503, and 504 response behavior.

## Expected files to touch

- `app/api/search/route.ts`
- `lib/search/prompt.ts`
- `lib/search/context.ts` only if request cancellation or measured context setup requires a small change
- A focused test file only if the repository's existing test setup supports it without introducing a new framework

Do not change the search UI, result schema, grounding model, Sanity schemas, seeded content, provider, dependencies, or environment-variable names.

## Requirements

1. Export `maxDuration = 60` from the Node.js search route.
2. Replace the hard-coded 25-second timer with named deadline constants and an internal deadline below the platform limit.
3. Combine the route deadline with `request.signal` and pass the resulting cancellation signal to initial-context retrieval and Gemini generation.
4. Filter MCP tools to expose only `groq_query`; fail safely if that required tool is unavailable.
5. Reduce `stopWhen: stepCountIs(8)` to a measured minimum, initially four steps.
6. Update the system prompt with a concise execution plan that avoids schema exploration and redundant GROQ calls while retaining lesson search, chapter-first matching, and transcript fallback.
7. Record coarse per-stage durations using a monotonic clock. Emit only safe operation names, elapsed milliseconds, final status, and model/tool step counts where available.
8. Distinguish a route deadline from a caller cancellation internally. Return the existing sanitized 504 only for the route deadline; do not expose internal exception details.
9. Always clear timers and close the MCP client, including on cancellation and failure.
10. Do not return raw MCP results, transcript arrays, Gemini output, credentials, or internal stack traces to the browser.
11. Preserve candidate Zod validation and `groundSearchCandidates` as the final authority for documents and timestamps.
12. Preserve all unrelated working-tree changes.

## Security considerations

- Keep `GOOGLE_GENERATIVE_AI_API_KEY` and `SANITY_API_READ_TOKEN` server-only.
- Do not log secrets, authorization headers, learner queries, generated GROQ, tool arguments, transcript text, or raw provider/MCP responses.
- Keep request-size and query-length validation unchanged.
- Keep tool access limited to the read-only Context MCP and narrow it to `groq_query`.
- Keep final server-side grounding so a model-proposed ID or timestamp is never trusted directly.
- Ensure cancellation and timeout cleanup do not leave outbound requests or MCP clients running.

## Acceptance criteria

- The route declares a 60-second maximum duration and retains a shorter internal deadline with a sanitized timeout response.
- Gemini receives only the `groq_query` MCP tool and can no longer spend a step exploring a schema already present in the system prompt.
- The maximum model/tool loop is reduced from eight to the lowest live-verified value that supports lesson results plus chapter-first/transcript-fallback video results.
- A caller that navigates away cancels the server-side model/context work.
- Safe timings identify setup, agent/tool, and grounding duration without exposing user content or secrets.
- At least three representative live searches, including one expected chapter match and one expected transcript fallback, complete without a Lopsis-generated 504 on both a cold request and warm requests.
- Returned cards remain Zod-valid and grounded to real lessons, courses, video IDs, and exact stored timestamps.
- Type checking, linting, and the production build pass.
- The development server starts successfully.

## Exact manual test steps

1. Ensure the existing server-only Google and Sanity credentials are present in `.env.local`.
2. Restart the Next.js development server so route and prompt changes are loaded.
3. Open `/search?q=hybrid%20search` and wait for the completed result state.
4. Confirm the page shows a grounded count and relevant lesson/video cards rather than the 25-second timeout message.
5. Open one lesson card and confirm it resolves to the stored Lopsis lesson.
6. Open one video-moment card and confirm the on-site player starts at the exact returned timestamp.
7. Search for a phrase known to appear in a chapter label and confirm a video result is returned from a chapter match.
8. Search for a phrase known only in a transcript chunk and confirm transcript fallback can still return a grounded video result.
9. Start another search, immediately navigate away, and confirm the UI does not show a stale result when returning.
10. Repeat the first query to exercise the warm initial-context path and compare its elapsed time with the first request.
